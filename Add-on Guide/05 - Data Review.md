# WoW Add-on Data Review (Editing, Data Files Only)

**Read `References/Pass Preamble.md` first; it governs everything below.** Pass Name: `the Data Review`. Write scope: **the `Data/{Game}/` folders the uploaded reports name, plus scratch files in the session's temp folder.**

The maintainer uploads Validate Data output (`References/Style Guide - Build Reference.md` → DIAGNOSTIC TOOLS → Validate Data), and this pass applies it to the add-on's static data one report at a time. **Cleanup comes first: every ID a client lacks leaves that client's folder**, so no flavor loads another expansion's items or spells. Three jobs ride along: correcting what the client contradicts, calling out restrictions its tooltips state that the data doesn't record, and checking the data against that client's own tables on wago.tools for anything it missed. Every file a report names leaves in the house layout (Style Guide → DATA → Data File Layout), dated.

**This pass asks nothing and hands back nothing to apply.** The reports and tables are the evidence: every change they support inside the write scope, it makes, and it says what it decided. Only a change outside `Data/{Game}/` becomes an issue.

## Workflow — five phases (0–4), all required

0. **Permissions** — per the preamble. The upload usually sits outside the add-on folder; reading it is in scope because the maintainer handed it over, and it reads without a prompt.

1. **Split the upload.** Never read a whole upload into context: split it by script into one scratch file per section, and work from those.
    - **A section is one client header line** (Build Reference → DIAGNOSTIC TOOLS → Report Header), which may cover several files, and the TSV blocks under it, each opening on a `STATUS` header row. Ignore everything else, dividers and notes included, and take each block's columns from its own header row, splitting on tabs only. An upload whose tabs became spaces waits for a re-paste.
    - **The header decides where a section goes.** Its title must be this add-on's; skip any other add-on's report. Its `Data` field names the one folder the section may change. A report proves only the folder its client loaded, so a Vanilla report never touches `Data/Discovery/` or `Data/Camelot/`, however alike their rows. One upload may hold several clients' reports. A block with no header line above it takes the nearest one before it, and an upload with none waits for the maintainer to name its folder.
    - **`Source` names each block's table on `ns`.** The one file in that folder declaring it is that block's file. The table's `ns.DIAGNOSTIC_DATA_SOURCES` entry shows how its IDs are reached.
    - A non-enUS report's names and tooltip text are translated, so take only its statuses and numeric columns.

2. **Work the sections in order, one at a time**, each validated before the next opens:
    1. **Prune what the client lacks.** Where a `NOT ON CLIENT` ID is what an entry is about (the key or lead field of a row, or its own slot in a plain list of IDs), the entry goes. Prune by script keyed on the flagged IDs, never by retyping (Style Guide → DATA → Flavor Folders), and correct any comment in the folder that still describes a pruned row. Where the ID is a detail of an entry about something else (a map value, a column, a recipe's reagent, a lone `ns` constant), read the code that looks it up and settle it in the file: drop the detail, or the whole entry where it means nothing without it. It is an issue only when no edit inside the folder leaves the code working. Only `NOT ON CLIENT` is grounds to prune; every other flagged row stays as it is.
    2. **Correct what the report states.** Where a row stores the very fact a report column or tooltip line states (a sell price, an amount restored, a required level or skill rank, an ability's learn level, an item's spell), a disagreeing value takes the client's. A trailing comment naming the row's own ID takes the client's name and keeps any note after it. Read the legend and the file's Notes first: a value that means something else, such as a level for another object or a computed figure, is never rewritten from a column that merely looks alike.
    3. **Sanity-check levels and zones.** A level stored for another object (an ability's row carrying the level its conjured item needs) is checked against that object's row wherever the upload carries it. **Where the add-on offers a row's item or spell for use, record every zone restriction a tooltip or spell description states that the data doesn't** ("Usable only inside Arathi Basin"), reusing the ID a row already pairs with that zone or citing where it found one, never an ID from memory. No API reports one, so an unrecorded restriction has the add-on offering an item where it can't be used. A table with no place for it makes it an issue, since adding one changes code. Drop a zone a row records that no tooltip or description states, and the other-flavor mark from a row the client still reports `OK`, except that one marked Season of Discovery's leaves `Data/Vanilla/` outright: the Classic Era client knows SoD's IDs, and SoD's items never belong in that folder.
    4. **Validate** per the preamble's Batch apply line. Its sanity check here is a script proving two things: the table's IDs are exactly its IDs before, less the pruned ones, and a diff moved nothing but pruned rows, corrected values, settled details, zones and marks, and fixed comments.
    5. **Date it and lay it out.** A report dates the file: under Last Validated, write today's date, then the client and build from the report header, replacing whatever was there (Style Guide → DATA → Data File Layout). The one exception is an older export whose item or spell block has no tooltip column: it can't confirm zones, so it leaves the date alone. A file not yet in the layout converts in the same edit: everything above the legend except the guard moves into the `How We Got the Data` block at the end. Old notes become plain-English Notes bullets, a real query moves under SQL (CMaNGOS) with its `TODO: Add SQL Query` marker otherwise, and every URL goes under its heading. Keep every fact, and drop only what restates the code. An undated pass line the report doesn't replace becomes `Undated`, then its client and build.
    6. **Give one status line**, then open the next section. For example: `Food-and-Water-Vanilla.lua: pruned 40, corrected 6, 1 zone recorded. Camelot and Discovery still hold 38 of the pruned IDs, left for their own client's report.`

3. **Cross-check against wago.tools and QuestieDB.** wago.tools serves each client build's own data tables as CSV. Check every folder the reports named against them for discrepancies and rows the data missed. With no upload, the maintainer names the folder and the build, and this phase runs alone.
    - **Use the report's own build.** Download each table the check needs into the session's temp folder from `https://wago.tools/db2/{Table}/csv?build={Client}.{Build}`, both numbers from the report header. An error instead of a CSV means wago.tools lacks that build, so name the one used instead. Layouts differ by client (Forever and Retail link items to effects through `ItemXItemEffect`), so read each file's header row, and calibrate every conversion on rows already confirmed before trusting it.
    - **Ask QuestieDB where it comes from.** Its raw tables (`https://raw.githubusercontent.com/Questie/QuestieDB/master/data/{Dir}/{dir}ItemDB.lua`, likewise `NpcDB`, `ObjectDB` and `QuestDB`, `{dir}` being `{Dir}` lowercased) cover every flavor but Mainline: `Classic` for Vanilla and Discovery, `TBC`, `Forever` for Camelot, `Wotlk` for Wrath, `MoP` for Mists. Discovery's own IDs are in none of them; they live only in `src/corrections/Sod/sodBaseItems.lua` (likewise `sodBaseNPCs`, `sodBaseObjects` and `sodBaseQuests`), so read those for a Discovery candidate. The raw tables come from CMaNGOS and predate the fixes in `src/corrections/` (`Era`, `Sod`, `Tbc`, `Forever`, `Wotlk`, `MoP`), so check an ID there before using its row, and the client's tables win any disagreement. Use it for what the tables can't say: whether a candidate drops, is sold or is a quest reward. A candidate with no source there and no spell in the tables that creates it is listed as likely unobtainable, not added. Each raw table used goes under the file's QuestieDB heading. Never script against the copy installed with Questie, which is compressed.
    - **Find each table's whole family.** A file's Notes and SQL say what belongs, so rerun their intent against these tables. Where they don't settle it, use what the file's rows share there (item class and subclass, the use spell's effect, its cooldown category) and name the test used. Every family member the table lacks is a candidate, unless a comment or `README-Notes.md` already rules it out. The Classic Era tables carry Season of Discovery's IDs too, so for `Data/Vanilla/` list the candidates that look like SoD's as ruled out.
    - **Check what the report couldn't.** A stored value the tables contradict takes the tables' value wherever the report didn't state the same fact. Where it did, the report wins, since it sees live fixes the tables lack. With no upload, an ID the folder holds that the tables lack stays, listed for the next Validate Data run, because only a report prunes.
    - **Move legacy data decisions.** Each `## Decisions` entry in `README-Notes.md` about a row kept out of a table in the write scope goes into that data file's How We Got the Data Notes, in every folder the reports named. Once it reads there in every folder a TOC lists, delete the entry, and the heading when the section is empty (Style Guide → README-NOTES).
    - **Add what belongs.** Every candidate the family test admits goes in, with values from these tables and each table's URL under the file's wago.tools heading, for the next Validate Data run to confirm. Validate as in phase 2 step 4, the IDs now being those before plus the added. Each file's status line names what was added and what was ruled out, and why.

4. **Report.** List the status lines in order, then the rows to re-run (every flagged row but `NOT ON CLIENT` and `TABLE MISSING`). Then write one issue in the preamble's fix-prompt format for each change that lies outside `Data/{Game}/`:
    - a flagged detail no in-folder edit settles, or a zone a table has no place for (phase 2);
    - a `TABLE MISSING` row, where the folder lacks a file or table (Style Guide → DATA → Flavor Folders);
    - an `"other"` table whose `Rows` count differs from the file's, when the cause isn't in the file.

    End with one line telling the maintainer to re-run Validate Data on that client. A clean run flags nothing.
