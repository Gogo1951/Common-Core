# WoW Add-on Data Review (Editing, Data Files Only)

**Read `References/Pass Preamble.md` first; it governs everything below.** Pass Name: `the Data Review`. Write scope: **every `Data/{Game}/` folder a TOC lists, plus scratch files in the session's temp folder.**

This pass checks the add-on's static data against each client's own game tables on wago.tools, and asks QuestieDB where things come from. **Cleanup comes first: every ID a client lacks leaves that client's folder**, so no flavor loads another expansion's items or spells. Three jobs ride along: correcting what the tables contradict, recording restrictions the item and spell descriptions state that the data doesn't, and adding rows the data missed. Every file it checks leaves in the house layout (Style Guide → DATA → Data File Layout), dated.

**No in-game run is needed.** The tables are the evidence. The pass asks the maintainer for a Validate Data run (`References/Style Guide - Build Reference.md` → DIAGNOSTIC TOOLS → Validate Data) only for what the tables and QuestieDB can't settle, and names the exact rows (phase 4). A Validate Data report the maintainer hands over anyway is applied first and wins over the tables, since it sees live fixes they lack.

**This pass asks nothing and hands back nothing to apply.** Every change the evidence supports inside the write scope, it makes, and it says what it decided. Only a change outside `Data/{Game}/` becomes an issue.

## Workflow — five phases (0–4), all required

0. **Permissions** — per the preamble. An upload usually sits outside the add-on folder; reading it is in scope because the maintainer handed it over, and it reads without a prompt.

1. **Pick the builds, and split any upload.**
    - **One client per folder.** `Data/Vanilla/` and `Data/Discovery/` are the Classic Era client's, `Data/Camelot/` WoW Forever's, `Data/TBC/` TBC Anniversary's, `Data/Mists/` MoP Classic's, `Data/Mainline/` Retail's. Use the build the maintainer names for a client, else the latest one wago.tools lists for it, and name it in that folder's first status line.
    - **Download each table the check needs** into the session's temp folder from `https://wago.tools/db2/{Table}/csv?build={Client}.{Build}`. An error instead of a CSV means wago.tools lacks that build: use the nearest build it serves for that client and name it, or, when it serves none, leave the folder for phase 4. Layouts differ by client (Forever and Retail link items to effects through `ItemXItemEffect`), so read each file's header row, and calibrate every conversion on rows already confirmed before trusting it.
    - **An upload is split by script, never read whole into context**: one scratch file per section. A section is one client header line (Build Reference → DIAGNOSTIC TOOLS → Report Header) and the TSV blocks under it, each opening on a `STATUS` header row, columns taken from that row and split on tabs only; everything else is ignored, and an upload whose tabs became spaces waits for a re-paste. Skip any section whose title isn't this add-on's. Its `Data` field names the one folder it may change, and `Source` names each block's table on `ns`. A non-enUS report's names and tooltip text are translated, so take only its statuses and numeric columns.

2. **Work every file in each folder, changed or not, one file at a time**, each validated before the next opens. Where a section of an upload covers the file, its rows go first, and its `NOT ON CLIENT` and columns count as the tables below.
    1. **Prune what the client lacks.** An ID absent from the table that defines its kind at that build (`Item` for items, `SpellName` for spells, and so on) is one the client lacks. Kinds the client tables don't hold, such as NPCs, quests and objects, are never pruned for absence. Where a missing ID is what an entry is about (the key or lead field of a row, or its own slot in a plain list of IDs), the entry goes. Prune by script keyed on the missing IDs, never by retyping (Style Guide → DATA → Flavor Folders), and correct any comment in the folder that still describes a pruned row. Where the ID is a detail of an entry about something else (a map value, a column, a recipe's reagent, a lone `ns` constant), read the code that looks it up and settle it in the file: drop the detail, or the whole entry where it means nothing without it. It is an issue only when no edit inside the folder leaves the code working.
    2. **Correct what the tables state.** Where a row stores the very fact a table column states (a sell price, an amount restored, a required level or skill rank, an ability's learn level, an item's spell), a disagreeing value takes the tables'. A trailing comment naming the row's own ID takes the client's name and keeps any note after it. Read the legend and the file's Notes first: a value that means something else, such as a level for another object or a computed figure, is never rewritten from a column that merely looks alike.
    3. **Sanity-check levels and zones.** A level stored for another object (an ability's row carrying the level its conjured item needs) is checked against that object's row. **Where the add-on offers a row's item or spell for use, record every zone restriction its description in the tables states that the data doesn't** ("Usable only inside Arathi Basin"), reusing the ID a row already pairs with that zone or citing where it found one, never an ID from memory. No API reports one, so an unrecorded restriction has the add-on offering an item where it can't be used. A table with no place for it makes it an issue, since adding one changes code. Drop a zone a row records that no description states, and the other-flavor mark from a row the client's tables still hold, except that one marked Season of Discovery's leaves `Data/Vanilla/` outright: the Classic Era client knows SoD's IDs, and SoD's items never belong in that folder.
    4. **Validate** per the preamble's Batch apply → How chosen prompts run. Its sanity check here is a script proving two things: the table's IDs are exactly its IDs before, less the pruned ones, and a diff moved nothing but pruned rows, corrected values, settled details, zones and marks, and fixed comments.
    5. **Date it and lay it out.** Under Last Validated, write today's date, then the source and the client and build it read: `wago.tools`, or `Validate Data` when an upload covered the file, replacing whatever was there (Style Guide → DATA → Data File Layout). A file not yet in the layout converts in the same edit: everything above the legend except the guard moves into the `How We Got the Data` block at the end. Old notes become plain-English Notes bullets, a real query moves under SQL (CMaNGOS) with its `TODO: Add SQL Query` marker otherwise, and every URL goes under its heading. Keep every fact, and drop only what restates the code.
    6. **Give one status line**, then open the next file. For example: `Food-and-Water-Camelot.lua (WoW Forever 1.60.1.70205): pruned 40, corrected 6, 1 zone recorded. Vanilla and Discovery still hold 38 of the pruned IDs, left for their own client's tables.`

3. **Cross-check and add what belongs.**
    - **Ask QuestieDB where it comes from.** Its raw tables (`https://raw.githubusercontent.com/Questie/QuestieDB/master/data/{Dir}/{dir}ItemDB.lua`, likewise `NpcDB`, `ObjectDB` and `QuestDB`, `{dir}` being `{Dir}` lowercased) cover every flavor but Mainline: `Classic` for Vanilla, Discovery and Camelot, `TBC`, `Wotlk` for Wrath, `MoP` for Mists. Discovery's own IDs are in none of them; they live only in `src/corrections/Sod/sodBaseItems.lua` (likewise `sodBaseNPCs`, `sodBaseObjects` and `sodBaseQuests`), so read those for a Discovery candidate. sodBaseItems carries no quest rewards, so a Discovery candidate with no drop or vendor there is unconfirmed, not likely unobtainable. `data/Forever/` is only a byte-for-byte copy of `Classic`, so Forever's own IDs are likewise missing; they live only in `src/corrections/Forever/generated/foreverBaseItem.lua` (likewise `foreverBaseNpc`, `foreverBaseObject` and `foreverBaseQuest`), so read those for a Camelot candidate. The raw tables come from CMaNGOS and predate the fixes in `src/corrections/` (`Era`, `Sod`, `Tbc`, `Forever`, `Wotlk`, `MoP`), so check an ID there before using its row, and the client's tables win any disagreement. Use it for what the client tables can't say: whether a candidate drops, is sold or is a quest reward. A candidate with no source there and no spell in the tables that creates it is listed as likely unobtainable, not added. Each raw table used goes under the file's QuestieDB heading. Never script against the copy installed with Questie, which is compressed.
    - **Find each table's whole family.** A file's Notes and SQL say what belongs, so rerun their intent against the client's tables. Where they don't settle it, use what the file's rows share there (item class and subclass, the use spell's effect, its cooldown category) and name the test used. Every family member the table lacks is a candidate, unless a comment or `README-Notes.md` already rules it out. The Classic Era tables carry Season of Discovery's IDs too, so for `Data/Vanilla/` list the candidates that look like SoD's as ruled out.
    - **Move legacy data decisions.** Each `## Decisions` entry in `README-Notes.md` about a row kept out of a table in the write scope goes into that data file's How We Got the Data Notes, in every folder a TOC lists. Once it reads there in all of them, delete the entry, and the heading when the section is empty (Style Guide → README-NOTES).
    - **Add what belongs.** Every candidate the family test admits goes in, with values from the client's tables and each table's URL under the file's wago.tools heading. Validate as in phase 2 step 4, the IDs now being those before plus the added. Each file's status line names what was added and what was ruled out, and why.

4. **Report.** List the status lines in order. Then **In-game check**: the rows the tables and QuestieDB couldn't settle (a client wago.tools serves no build for, or a fact only the live client shows), each with its client and what a Validate Data run there would settle, or `None needed.` when there are none, which is the normal result. Then write one issue in the preamble's fix-prompt format for each change that lies outside `Data/{Game}/`:
    - a missing ID's detail no in-folder edit settles, or a zone a table has no place for (phase 2);
    - a folder a TOC lists that lacks a file or table its siblings declare (Style Guide → DATA → Flavor Folders), or, from an upload, a `TABLE MISSING` row;
    - from an upload, an `"other"` table whose `Rows` count differs from the file's, when the cause isn't in the file.

    A clean run flags nothing.
