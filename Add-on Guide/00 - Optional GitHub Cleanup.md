# GitHub Cleanup (Optional): New Add-on Scaffold or Existing Repo Check

**Read `References/Pass Preamble.md` first; it governs everything below.** Pass Name: `the GitHub Cleanup`. Two modes, asked first if the request doesn't say:

- **New add-on**: create the add-on on [Common-Core](https://github.com/Gogo1951/Common-Core) from the canonical repos and the Style Guide. Write scope: **the new add-on's folder only.** The output is a complete, loadable skeleton that already passes the Code Review's structural checks; feature logic comes later. The add-on's master-list row is *proposed* in Guide Feedback, never written here.
- **Existing add-on**: check that every scaffolding file and GitHub setting in the New Add-on Checklist below is in place. Write scope: **nothing.** It reads the repo on GitHub with `gh` (the files on `main`, the settings, the secret *names*, never their values) and reports each gap with its fix: a missing setting as a `gh` command in a `bash` block for the maintainer to run, and a missing or wrong repo-only file (`.pkgmeta`, `.luacheckrc`, `LICENSE`) as its complete corrected contents to paste into GitHub, per `08 - Prelaunch Review.md` → Packaging. The one thing it does itself is checklist step 8's board backfill: it adds the repo's missing issues and PRs to the project board, which touches no repo file, and reports how many it added. Shared files are never edited here: a drifted one is fixed by running Common-Core's sync script (Style Guide → COMMON-CORE). Launch in the add-on's folder and run `01 - Local Setup.md` → Session Prep step 0 first; the rest of Session Prep isn't needed, since this mode reads GitHub, not the folder. A repo with nothing missing gets a one-line report.

## New Add-on Checklist

Every add-on is built on Common-Core (Style Guide → COMMON-CORE), and this list is what the existing-add-on mode checks. In new-add-on mode, this pass does the file work of checklist steps 2–5 in Phase 2; every commit, the PR and the tag go through `12 - Create Release Notes & PR.md` and its identity gate; the GitHub steps (1, 6, 7, and 9's dry run and tag) are the maintainer's. Step 8's board check runs once the repo exists.

1. Create the repo under `Gogo1951` as public, with `main` as the default branch.
2. Write `.pkgmeta` per Style Guide → REQUIRED LIBRARIES → .pkgmeta.
3. Run `~/Common-Core/scripts/sync-addon-files.sh` on the new add-on folder and commit. The script skips a folder with no `.pkgmeta`, hence step 2 first.
4. Write `.luacheckrc` per Style Guide → LINTING. Fix warnings rather than widening the config.
5. If the add-on has offline tests, the entry point is `Tests/Run.lua`, run from the add-on root with `lua5.1` (Style Guide → LUA 5.1). `.pkgmeta` keeps `Tests/` out of the zip.
6. Add the `CF_API_KEY` and `WAGO_API_TOKEN` secrets. Never add `GITHUB_OAUTH` or `GITHUB_API_TOKEN`; Common-Core's `package.yml` explains why.
7. Apply the standard repo settings:
    - a ruleset named "Protect main" on the default branch that blocks force pushes and deletion (don't require PRs or status checks: the release bot pushes to `main`);
    - Dependabot alerts and security updates;
    - secret scanning with push protection;
    - private vulnerability reporting;
    - CodeQL default setup;
    - read-only default workflow token;
    - squash merge only, with head branches deleted automatically.
8. Put the repo on the [Gogo Add-ons project board](https://github.com/users/Gogo1951/projects/6). Every issue and PR belongs there. No per-repo setup is needed: the synced issue forms name the board, and Common-Core's scheduled `project-board.yml` sweep adds the rest for every repo that has the `issue-labels.yml` caller. The sweep only runs when Common-Core holds the `PROJECT_TOKEN` secret (a classic personal access token with the `project` scope); without it every run skips with a warning. Check both: `gh secret list -R Gogo1951/Common-Core` names `PROJECT_TOKEN`, and every issue and PR in the repo is on the board. Add any that are missing with `gh project item-add 6 --owner Gogo1951 --url <issue or PR URL>`.
9. Open a PR and confirm CI passes. Then use **Run workflow** on "Package and release" in the Actions tab for a dry run, which builds the zip and uploads nothing. Only then push the first tag.

## New-add-on workflow — four phases (0–3), all required

0. **Permissions.** The template's write grant is "the folder the session was launched in" — and the new add-on's folder doesn't exist yet, so scaffold sessions launch **in the target flavor's `Interface/AddOns` folder**: launched there, the grant covers the AddOns folder, including the folder Phase 2 creates. Terminal: run `wowclaude` from `Interface/AddOns` (session-only). Desktop app: run `01 - Local Setup.md` → Session Prep step 0 from `Interface/AddOns` (renders that folder's `.claude/settings.local.json`; one approval, plain Yes). There `{{ADDON}}` renders as `AddOns`, which is harmless. Later sessions launch in the new add-on's folder as usual, and its first desktop-app session seeds there via step 0. The rest of Session Prep doesn't apply: the scaffold writes the TOCs right, and there's no repo to pull yet.

1. **Intake — ask before creating anything.** Read the Style Guide, `References/Style Guide - Build Reference.md` and the master list first, then ask the maintainer, per the Style Guide → ASKING THE MAINTAINER format:
    - **Full Name, Short Name, repo name, and folder name** (Style Guide → ADD-ON NAMES; folder = `.pkgmeta` `package-as` = the Lua `ADDON_NAME` vararg; check the master list so nothing collides). If brand and folder differ, note the canonical in-Lua identity (see Style Guide → NAMING).
    - **Tagline** (every TOC's `## Notes:`, enUS `OPTIONS_DESCRIPTION`, and the stub README's pitch).
    - **Category** — exactly one, from the live wiki list (<https://warcraft.wiki.gg/wiki/Addon_Categories>).
    - **Target marker** — or player-only. Check the master list's Target marker column for collisions before offering options.
    - **Mini-map button?** Determines the two optional libraries, the button and menu files (MINIMAP MENU), and the Enable Mini-map Button toggle.
    - **Slash command** — every add-on has one, so ask for the *literal*, not whether to have it. Check the master list's Slash command column for collisions before offering options, and record the assignment as a routine Guide Feedback item. The mandated `/Commands` copy and the combat guard come with it (see Style Guide → OPTIONS PANEL → Slash Commands and Combat Guard). A *feature* command is still request-only and recorded nowhere.
    - **Feature list** — one line per planned feature, to name the `Features/{Feature-Name}.lua` / `Options/Options-{Feature-Name}.lua` stubs. A single-feature add-on may keep its pipeline in `Core.lua` (Style Guide → FILE STRUCTURE, single-feature add-ons) — ask which shape the maintainer wants.
    - **Release IDs** — `X-Curse-Project-ID` / `X-Wago-ID` if the listings exist; otherwise scaffold with placeholder comments (a placeholder ID is a Prelaunch Blocker, so it will be caught before release).

    Do not create anything until answers are in.

2. **Scaffold.** Build the folder per the Style Guide's REPOSITORY LAYOUT, using the live reference repos as a shape reference and the Style Guide's rules as the standard (its opening rule governs any rule-vs-live-file conflict):
    - **Structure:** Connoisseur is the end-to-end template.
    - **Options panel:** copy each piece from the live reference its Style Guide or Build Reference section names (Label-Beside-Control Rows, Item Lists, Opening the Panel), and carry the layout width constants into `Data/Data.lua`. Register the one options slash command and put the `InCombatLockdown()` gate at the top of `ns:OpenOptionsPanel` per Style Guide → OPTIONS PANEL → Slash Commands and Combat Guard (live reference for the gate: Play It Forward).
    - **Diagnostics:** copy Magic Eraser's `Diagnostics/` folder verbatim (leaving out `Validate-Data.lua` if the add-on has no data files) and re-author per Style Guide → DIAGNOSTIC TOOLS → Live Reference; `DIAGNOSTIC_EVENT_EXCLUDE` starts empty.
    - **Mini-map button** (if chosen): the button and its menu from Tracking Eye, per Style Guide → MINIMAP MENU → Moving a Tooltip to a Menu, steps 1–2; adjust identity values.
    - **`.pkgmeta`:** copy the live `Thanks-for-the-Buff` file (it carries the AceDB externals — see Style Guide → REQUIRED LIBRARIES → .pkgmeta); set `package-as`; externals and the ignore list follow that section.
    - **Shared files:** with `.pkgmeta` written, run `~/Common-Core/scripts/sync-addon-files.sh` on the new folder (checklist step 3); Session Prep step 0 has just brought the clone up to date. It writes both workflow callers, `.gitignore` and `.gitattributes`; never write or edit them by hand.
    - **`.luacheckrc`:** per checklist step 4, filling `read_globals` and `globals` for this add-on.
    - **`LICENSE`:** write `References/Canonical Files/LICENSE.txt` with `{{YEAR}}` set to the current year. The holder is always `Gogo1951`, never a real name.
    - **TOCs:** one per current target, per TOC FILE FORMAT → Flavor TOCs (`_Vanilla.toc`, `_TBC.toc`, `_Camelot.toc`; never an unsuffixed one), identical except as that section allows — `## Version: @project-version@`, both release IDs (or placeholders), the full `## Category-*` locale block copied verbatim from the wiki, single `## SavedVariables: AddonNameDB`, the guide's footer block. Set each `## Interface:` to its client's number hard-coded in `01 - Local Setup.md` (Session Prep step 1) — see Style Guide → TOC FILE FORMAT → Interface Versions.
    - **`Data/Flavor.lua`:** write the file verbatim from `References/Canonical Files/Flavor.lua`, listed first in every TOC's `# Data` block. Static data follows DATA → Flavor Folders from the first row: all seven folders, holding the same table names, each suffixed with its folder's name. Each file follows DATA → Data File Layout, its Last Validated reading `Never.` until Validate Data runs on that client.
    - **Core wiring:** central event dispatcher exporting `ns.EVENT_NAMES`; AceDB creation at the SavedVariables init point per Style Guide → SAVED VARIABLES. **Pick the model by that section's selection rule** — Per-Character if the add-on stores anything genuinely about the character (omit `AceDB:New`'s third argument; presentation in `ns.db.global`, per-character state and its features' settings on the profile), Simple if it doesn't (pass `true`; everything in `ns.db.profile`). Wire the profile callbacks either way. `ns.RegisterOptionsPanels()` called right after `AceDB:New`; `ns.PALETTE` in `Data/Data.lua`; `ns.DATABASE_DEFAULTS` in `Data/Default-Settings.lua`; welcome message via `PrintMessage`.
    - **Locales:** `enUS.lua` with the standard keys (`ADDON_TITLE`, `ADDON_SHORT_NAME`, `CHAT_LOADED`, `CHAT_OPTIONS_IN_COMBAT`, `OPTIONS_DESCRIPTION`, `OPTIONS_COMMANDS_HEADER`, `OPTIONS_COMMAND`, `OPTIONS_COMMAND_DESCRIPTION`, `OPTIONS_VERSION`, options strings), plus the other ten locale files as key-complete translations of the initial enUS strings, leaving English only where `07 - Localization Review.md` → When a value may stay English allows. No key names a spell, item, skill, zone, class or Blizzard UI label: store its ID in the flavor folders and ask the client for the name (Style Guide → GAME NAMES).
    - **READMEs:** stub `README.md` (H1 title, the tagline, GitHub/Discord links), stub `README-Technical.md` (title + the cross-link line), and `README-Notes.md` per Style Guide → README-NOTES with `## Exceptions` reading `None.`, so the repo matches REPOSITORY LAYOUT from day one. `09 - Optional Create README.md` and `10 - Optional Create README-Technical.md` replace the first two properly later.
    - Run StyLua-default formatting, with `--syntax lua51`, over every Lua file outside `Includes/` (CI checks it with StyLua 2.5.2).

3. **Register and report.** Draft the add-on's master-list additions — its Quick reference table row and a per-add-on detail entry (links may be placeholders until listings exist; note them as such) — and output them as routine data items in the Guide Feedback section, exact text ready to apply and undated. This pass never writes the master list. Then report: what was created, every placeholder that still needs a real value, the checklist steps still open, and the next step — enter the pipeline at `02 - UX Review.md` once feature logic exists.
